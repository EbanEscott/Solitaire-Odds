# Experiment Results

This document describes how to treat experiment outputs, how to compare runs, and which results should be promoted beyond the runtime artifact tree.

## Result Surfaces

The experiments stack has three different output surfaces, and they serve different purposes.

### Canonical Per-Run Outputs

The canonical output of one completed experiment run lives under `experiments/runtime/artifacts/<run_id>/`.

That artifact tree contains task-level outputs such as:

- collection summaries and captured `episode*.log` files
- training summaries, metrics, and checkpoints
- evaluation shard summaries
- generated markdown, JSONL, Parquet, DuckDB, and SQL report artifacts

If the question is "what did this run produce?", the first place to look is the run artifact tree.

### Operational Runtime Outputs

`experiments/runtime/work/` is an operational area rather than the canonical result surface.

It is the right place for:

- `doctor` outputs such as `runtime_health_report.md` and `runtime_health_report.json`
- maintenance logs
- temporary inspection outputs created while operating the driver locally

It is useful for operators, but it is not the place to treat as the final published result for an experiment family.

### Registry State

`experiments/runtime/registry/` is persistence and lineage state.

It records runs, tasks, attempts, heartbeats, and artifact pointers. It supports resume and inspection, but it is not itself the presentation surface for results.

## Promotion Guidance

Generated run artifacts are the source of truth for raw experiment outputs. Promotion is the next step taken only when a result is stable enough to matter outside one local run directory.

Current promotion rules:

- Treat `experiments/runtime/artifacts/` as the canonical generated output for each run.
- Treat notebooks as consumers of DuckDB and Parquet outputs, not as the source of truth.
- Promote only distilled summaries, comparisons, or conclusions that are stable enough to keep under version control.
- If a result affects the repo-wide player leaderboard, the canonical published summary belongs in the root `README.md`.
- If a result is experiment-specific, promote it to a tracked markdown summary or tracked notebook outside `experiments/runtime/`.

## Recommended Experiment Program

The manual findings under `../neural-network/results/` were useful for exploration, but they should now be treated as historical notes rather than canonical performance results. Going forward, the source of truth should be experiment-driver artifacts and generated reports under `experiments/runtime/artifacts/`.

The current driver evaluates one level per spec. That is enough to build a reliable cross-level study, but the study should be expressed as a family of comparable runs that hold training constant and vary only `evaluation.level`.

### Primary Goals

- Establish a canonical baseline that is reproducible from a named spec, `run_id`, fixed checkpoint lineage, and fixed seed range.
- Replace ad hoc per-level markdown notes with comparable driver-generated reports for Levels 2 through 10.
- Separate data questions from model questions by avoiding runs that change dataset, architecture, and search budget at the same time.
- Measure generalization, not just same-level fit, by evaluating the same trained checkpoint across a ladder of harder levels.
- Keep model-quality gains tied to cost by comparing win rate together with evaluation runtime and search budget.

### Recommended Experiment Ladder

| Family | Question | Suggested setup | Success signal |
| --- | --- | --- | --- |
| Driver smoke | Is the end-to-end workflow stable enough for longer runs? | Start with a small `mlp_fresh_data_demo`-style run at Level 2 using tiny collection and evaluation counts. Confirm that `plan`, `run`, `status`, and resume all behave as expected. | Collection, training, evaluation, and reporting all complete cleanly, and a resumed run skips succeeded tasks instead of duplicating work. |
| Canonical baseline sweep | What is the current baseline across Levels 2 to 10? | Pick one baseline checkpoint family, keep `mcts_*` settings fixed, and run one evaluation spec per target level with the same seed-band policy. Use the cross-run comparison outputs to assemble the level ladder. | A single comparable table exists for Levels 2 through 10, all generated by the driver with the same evaluation budget. |
| Fresh vs. archived data | Does fresh collection beat archived logs at the same data budget? | Compare `dataset.kind=archived_episode_logs` against `dataset.kind=run_collection_episode_logs` while holding architecture, epochs, and evaluation settings constant. Start at Levels 2 to 4 before widening the sweep. | Fresh data shows a repeatable win-rate gain on matched evaluation seeds, or it clearly fails to justify the extra collection cost. |
| Curriculum depth sweep | How far up the endgame curriculum should training go? | Train a family of checkpoints whose highest training level increases stepwise, such as Level 2 only, then through Levels 4, 6, 8, and 10. Evaluate every checkpoint across the same Level 2 to 10 ladder. | The chosen curriculum frontier improves harder levels without obvious regression on easier ones. |
| Architecture comparison | Does the GNN materially outperform the MLP when data and budget are matched? | Reuse the same dataset lineage and evaluation ladder for both `mlp_policy_value` and `gnn_policy_value`. Keep batch size, epoch count, and search budget as close as practical. | The GNN either wins clearly on the target level band or the MLP remains preferable because it is simpler for similar results. |
| Search-budget sweep | Which inference budget is worth paying for? | Freeze the best checkpoint, then sweep `mcts_simulations`, `mcts_max_depth`, and, only if needed, `mcts_cpuct`. Run this after the model and dataset decisions are mostly settled. | The team identifies the smallest search budget that is near the performance plateau for the chosen model. |
| Holdout confirmation | Do the apparent winners survive new seeds? | Re-run the top two or three configurations on a disjoint seed band after the earlier experiments identify likely winners. | Ranking is stable enough that promotion decisions do not depend on one lucky seed block. |

### Practical Rules For Comparable Runs

- Change one major variable per experiment family. For example, do not compare MLP versus GNN while also changing dataset lineage and search budget.
- Reuse fixed seed bands. A simple pattern is one smaller development seed band for quick iteration and one larger confirmation band for final comparisons.
- Prefer archived logs when comparing architectures, because frozen data isolates model differences more cleanly than fresh collection.
- Prefer fresh collection when testing whether the current generator and curriculum produce better training data than the archived baseline.
- Encode the important knobs in `experiment_id` and `run_id`, such as family, data source, training frontier, evaluation level, and search budget.
- Promote only runs that beat the current baseline on the target level band without creating obvious regressions on easier levels.

### Near-Term Recommendation

If you want a focused sequence rather than a broad sweep, start with this order:

1. Build one canonical MLP baseline ladder for Levels 2 through 10.
2. Run a fresh-vs-archived comparison at a low-to-mid level band such as Levels 2 through 4.
3. Run a curriculum-depth sweep once the preferred data source is clear.
4. Compare MLP and GNN on the winning dataset and curriculum setup.
5. Finish by tuning the search budget on the best checkpoint instead of tuning search early.

## Starter Specs

The following tracked specs turn the first experiment families into runnable starting points.

- `experiments/specs/baseline_mlp_level2_dev.json` seeds the canonical baseline ladder with one fixed-checkpoint Level 2 evaluation. Copy it for Levels 3 through 10 by changing only `experiment_id`, `evaluation.level`, and `evaluation.service_port`.
- `experiments/specs/archived_mlp_l2to4_level4_dev.json` is the archived-data side of the fresh-vs-archived comparison.
- `experiments/specs/fresh_mlp_level4_dev.json` is the fresh-collection side of the fresh-vs-archived comparison.
- `experiments/specs/archived_gnn_l2to4_level4_dev.json` is the matched GNN side of the architecture comparison once the archived MLP run is in place.

Each starter spec uses a development seed band rather than a final confirmation band. That keeps the first sweep cheap enough to iterate on while still producing multiple evaluation shards and a meaningful report.

## Naming Convention

Use names that make cross-run comparison readable without opening the JSON.

### Spec Filenames

Use underscore-separated filenames in `experiments/specs/`:

`<family>_<model>_<data-scope>_<eval-scope>_<band>.json`

Examples:

- `baseline_mlp_level2_dev.json`
- `archived_mlp_l2to4_level4_dev.json`
- `fresh_mlp_level4_dev.json`
- `archived_gnn_l2to4_level4_dev.json`

### Experiment IDs

Use the same information in hyphen form inside the JSON:

`<family>-<model>-<data-scope>-<eval-scope>-<band>`

Examples:

- `baseline-mlp-level10ckpt-eval-level2-dev`
- `archived-mlp-train-l2to4-eval-level4-dev`
- `fresh-mlp-collect-level4-eval-level4-dev`
- `archived-gnn-train-l2to4-eval-level4-dev`

### Run IDs

Use the date plus the `experiment_id` plus a short retry suffix:

`<yyyymmdd>-<experiment-id>-r<nn>`

Examples:

- `20260530-baseline-mlp-level10ckpt-eval-level2-dev-r01`
- `20260530-archived-mlp-train-l2to4-eval-level4-dev-r01`
- `20260530-fresh-mlp-collect-level4-eval-level4-dev-r01`

This keeps the spec identity stable while still allowing repeat runs, disjoint seed bands, or later reruns after driver changes.
